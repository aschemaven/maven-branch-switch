== Motivation

A few Maven 4-specific plugins and components currently carry their Maven 4 code on the default `master` branch, with a `<repo>-3.x` branch for Maven 3.
That is the reverse of the agreed strategy: *default is Maven 3*, and Maven 4 is a separate branch until user migration to Maven 4.0 has made good progress.

The goal is to make the Git layout match that intent, so that a casual clone of any of these repos lands on the Maven 3 line, and the Maven 4 work is clearly marked as the exception.

Hervé Boutemy filed the tracking issue on 2026-09-20 and asked on Slack (#maven) for someone to lead the actual Git work, including branch-protection updates and README links.

== Scope

Per repository, swap the two branch roles:

. the current `master` (Maven 4 code) becomes `<repo>-4.x`
. `<repo>-3.x` (Maven 3 code) becomes `master`
. the default branch and branch protection point at the new `master`
. `README.md` links, `maven-sources/default.xml`, milestones and release-drafter follow

=== Naming: `master`, not `main`

The target branch name stays `master`, not `main`.
Martin Desruisseaux proposed renaming to `main` to avoid surprising Maven 4 users (2026-09-25); Hervé Boutemy and Gerd rejected mixing that in here.
Maven's convention is `master`, and a move to `main`, if it ever happens, should be a separate global migration, not a side effect of this one.

== Method: rename, not force-push

*Decision (Gerd, 2026-09-25): rename in every case, never force-push.*

Rename (preferred):: GitHub's branch rename automatically retargets open PRs whose base was the renamed branch, and updates references.
Renaming `master` -> `<repo>-4.x` carries all ~45 open PRs with the Maven 4 code to `<repo>-4.x` -- which is exactly correct, since they *are* Maven 4 work.
No PR loses its merge base.

Force-push (rejected):: the team precedent for maven-site-plugin (Hervé, Slack 2026-04-03: saved `master-20260403`, then force-pushed `-3.x` onto `master`) tears every open PR off its merge base and turns it into a conflict.
Only defensible with a manual PR-retarget beforehand, and still worse than a rename.
We do not use it.

Rename vs. default-branch switch (two different operations):: renaming the current default branch retargets the open PRs; merely pointing the default at a different existing branch does *not* (details and source in <<default-branch-mechanism>>).
So the order is fixed: rename first (this migrates the PRs), and flip the default pointer back to `master` only as the last step, once both branches exist.

[[default-branch-mechanism]]
The branch *rename* is what migrates the open PRs; a default-branch *switch* (the ASF Gitbox "boxer" action) only moves the pointer and does *not* retarget PRs.
So the rename is the PR-migrating step -- it needs repo admin, not PMC/boxer -- and the final default pointer back to `master` is set via `.asf.yaml`.
For the mechanism, the INFRA/boxer sources and the full reasoning, see the companion page xref:background-rename-vs-default-branch.adoc[Background: branch rename vs. default-branch switch].

== Who executes the protected-`master` part (open coordination question)

Creating branches and editing `.asf.yaml` / `README.md` / `default.xml` are within committer rights.
Two things touch the *protected default branch*: the *renames* of `master` (the PR-migrating part) and the final *default pointer* back to `master`.
Both need repo admin, so INFRA does them in one go -- the two renames and, right after, setting the default back to `master` (the renames leave it on `<repo>-4.x`).
No PMC/boxer, and nothing about the default goes into `.asf.yaml`: the repos carry no `github.default_branch` today and we add none.
The mechanism (why a rename migrates PRs but a default-switch/boxer does not) is in the companion page xref:background-rename-vs-default-branch.adoc[Background].

[NOTE]
====
*Decided 2026-10-06:* INFRA (Bob Thomson) approved *approach A* -- INFRA performs the renames, no boxer/PMC step -- and is fine to execute from ~16 October (after Community over Code).
Options B and C below are kept for the record.
====

Three alternatives, in order of preference:

A. *Preferred -- INFRA performs the renames and the default flip.*
  INFRA performs the two protected-`master` renames per repo (`master` -> `<repo>-4.x`, then `<repo>-3.x` -> `master`) -- which migrate the open PRs (INFRA-28244) -- and sets the default branch back to `master` right after.
  We (committers) do everything else: branch prep, the `.asf.yaml` protection/metadata, `README.md`, the default-sourced `.github/` content, `default.xml`, communication, verification.
  No PMC/boxer step, and no `github.default_branch` in `.asf.yaml`.
B. *Fallback -- temporary admin for Gerd.*
  INFRA grants Gerd admin on the 9 repos for the migration; Gerd does the renames and sets the default himself; admin is dropped again afterwards.
  One grant instead of per-repo INFRA turnaround.
C. *Variant of A with a PMC action.*
  As A, but the final default pointer back to `master` is flipped by an (I)PMC member via ASF Gitbox "boxer" (its "Change default branch" action is (I)PMC-only), instead of by INFRA.

[source,yaml]
.`.asf.yaml` on the new `master` -- the repo's current `master`, branch-swapped
----
github:
  # ... everything the repo's current master already declares, unchanged ...
  protected_branches:
    master: { }
    <repo>-4.x: { }        # was <repo>-3.x on today's master
  pull_requests:
    del_branch_on_merge: true
  features:
    issues: true
  # NO github.default_branch -- the repos have none; INFRA sets the default
----

[NOTE]
====
The rule is simple: make the `<repo>-3.x` branch's `.asf.yaml` *identical to the repo's current `master`'s*, with the only change being the protected-branch name (`<repo>-3.x` -> `<repo>-4.x`).
That preserves the repo's existing protection/merge/metadata and introduces nothing new -- in particular no `github.default_branch`, and no stricter required checks than `master` already has.
Branch-only extras that `master` lacks (e.g. a stray `notifications.jira_options`) are dropped to stay identical; flag every such removal in the PR so maintainers can object.
====

== Timing: when to swap

*Decided:* all nine repos in one coordinated session with INFRA on *Sunday 2026-10-18* (after Community over Code EU), outside any open staging/release vote.

Background: gnodet had asked to defer and swap each repo only after its own next release (staggered, 2026-09-25); his one real concern was the open PRs, which the rename retargets automatically, so he withdrew it (gnodet, 2026-10-06: "my main point was the PR, if they are automatically retargeted, it goes away").
Hervé's guidance (2026-10-06): the only thing that matters is not to change a branch during a vote; otherwise it is easy enough to just do it once INFRA is available, which is the real coordination needed.
So we do it all-at-once -- one INFRA session -- rather than staggered.

The committer-side `.asf.yaml` + `README.md` PRs are pre-staged (see the runbook) and approved by 2026-10-16, so they can be merged immediately around the switch.

[IMPORTANT]
====
*Hard precondition:* the swap runs *only outside an open staging/voting window* for the affected repo.
A rename during a live vote would move the branch a voter is checking out from under them.
====

== Per-repository runbook (draft)

=== Pre-staging the committer-side PRs

The `.asf.yaml`, `README.md` and `.github/` changes (branch protection, metadata, branch links/badges, default-sourced repo config) are committer-side work under approach A, and they are raised and reviewed *ahead* of the swap so nothing has to be written under time pressure during the INFRA session:

. *Raise* one *non-draft* PR per repo with the `.asf.yaml`, `README.md` and `.github/` changes, based on `<repo>-3.x` (the branch that becomes the new `master`).
Mark it as held -- title prefix `[HOLD until maven-sources#57 swap]` plus a comment stating when it merges -- following the project's `[NOT FOR MERGE]` convention.
. *Get it approved* ahead of the switch (target: *2026-10-16*).
`maven-filtering`'s protection is `{ }` (no required review), so a committer self-approves/merges there; other repos may require a second committer -- check each repo's `.asf.yaml` when templating.
. *Merge* it immediately around the rename on *2026-10-18* -- it restores the repo's branch protection and metadata on the new `master`.
The default itself is set back to `master` by INFRA as part of the renames, not by this PR.
The `.asf.yaml` change is *inert* until `<repo>-3.x` becomes the default branch, so an early merge is harmless.

`maven-sources/default.xml` is deliberately *not* pre-staged this way: an early merge would break `repo sync` (it would reference a not-yet-existing `<repo>-4.x`), so it is done once for all repos right after the swap (see below).

`.github/` is read from the default branch too, so the pre-staged PR also carries it over (otherwise the swap silently drops it): *repo-wide, default-sourced* pieces -- issue templates, scheduled workflows (e.g. `stale`), the PR template, the release-drafter *workflow* (its branch filter) -- are taken from the current `master`; *line-specific* pieces -- `dependabot`, the release-drafter *config*, the `maven-verify` CI -- stay the Maven 3 line's.

=== Swap window (per repo, coordinated with INFRA)

For each of the 9 repos, in order:

. confirm `<repo>-3.x` is the intended Maven 3 content and is green
. *(INFRA)* rename `master` -> `<repo>-4.x` (retargets the open Maven 4 PRs automatically)
. *(INFRA)* rename `<repo>-3.x` -> `master`
. *(INFRA)* set the default branch back to `master` (the renames left it on `<repo>-4.x`)
. merge the pre-staged `.asf.yaml` + `README.md` PR -- restores the repo's branch protection and metadata on the new `master`
. verify: the ~N open PRs now target `<repo>-4.x`; a fresh clone lands on the Maven 3 line; default is `master`
. post a short heads-up on each retargeted PR, so the automatic base change has context -- templated and scriptable across the ~N PRs (see <<pr-heads-up>>)
. update milestones (branch name in description) and release-drafter config
. announce on the repo / dev@ list

[NOTE]
====
The default-branch flip is INFRA's (they have admin and are doing the renames); no `.asf.yaml` `github.default_branch` and no (I)PMC boxer step are involved.
What still needs a pilot check is whether merging the `.asf.yaml` re-triggers asfyaml to apply the `protected_branches` block on the new `master`; if not, a trivial push to `master` nudges it.
====

=== After all repos are swapped (once)

. one `maven-sources/default.xml` PR covering *all* swapped repos (see below), merged via PR -- inverting every role in a single change
. verify `repo sync` is green again

[[pr-heads-up]]
.PR heads-up comment (template, posted after the rename)
****
As part of apache/maven-sources#57 this repo's default branch was switched back to Maven 3.
GitHub retargeted this PR's base from `master` to `<repo>-4.x` (where the Maven 4 code it targets now lives) -- nothing needed from you, just flagging so the base change isn't a surprise.
Details: apache/maven-sources#57 / this Confluence page.
****

Drive it mechanically across the open PRs with `gh pr list --repo apache/<repo> --state open` + `gh pr comment`, once the base has actually moved to `<repo>-4.x`.
The pilot PR (maven-filtering#363) already got an advance variant of this note.

==== `maven-sources/default.xml`

The manifest currently pins the roles inversely and must be inverted with the swap.
Example for the core plugins (same shape for packaging + shared):

[source,xml]
.before
----
<project path='plugins/core/maven-clean-plugin'   name='maven-clean-plugin.git' revision="maven-clean-plugin-3.x" />
<project path='plugins/core-4/maven-clean-plugin' name='maven-clean-plugin.git' />
----

[source,xml]
.after
----
<project path='plugins/core/maven-clean-plugin'   name='maven-clean-plugin.git' />
<project path='plugins/core-4/maven-clean-plugin' name='maven-clean-plugin.git' revision="maven-clean-plugin-4.x" />
----

The `core/` (Maven 3) row drops its `revision=` and follows the new default `master`; the `core-4/` (Maven 4) row pins the new `<repo>-4.x` branch.
This file breaks `repo sync` while it still references a renamed-away branch, so it is updated for all repos together in one PR right after the swap window -- a short, known `repo sync` gap for the already-swapped repos is accepted (dev tooling only).

== Communication

The migration changes visible behavior (a fresh clone lands on a different line; `master` moves), so it must be accompanied by communication, not just executed.

Principles:

* every outward step references *this Confluence page* as the single source of truth
* announce behavior changes as *advance notice*, before they happen -- especially the `master` switch, so nobody is surprised mid-work
* keep it low-noise: occasional, milestone-driven posts, not a running commentary
